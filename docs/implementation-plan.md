## 4. Database schema and RLS

### 4.1 Approach

- **Read path:** RLS on every table. Server components query with the *user's* session, so RLS is the
  second boundary behind the server action's own checks (spec §7.4, §10).
- **Simple writes** (music metadata, events, shares, profile) go through RLS-protected inserts and updates from
  server actions.
- **Multi-row or versioned writes** (add, remove, or reorder plan items, edit plan title, duplicate plan) go
  through Postgres functions marked `SECURITY INVOKER`. They run in one transaction, check
  `plans.version`, write `plan_activities`, and *still pass through RLS*.
- **Permission helpers** are small `SECURITY DEFINER` SQL functions:
  - `is_active_member()`, `is_admin()`, `can_view_plan(id)`, `can_edit_plan(id)`, `is_plan_owner(id)`.
  - This avoids the classic `plans ↔ plan_shares` RLS infinite recursion.
  - They are fast because each one is a single indexed lookup.
- **Policy performance:** policies call `(select auth.uid())`, so Postgres evaluates it once per query instead of
  once per row.
- **Anonymous role:** gets **no** table privileges at all. Public links are resolved only on the server (§4.6).
- **Explicit grants:** new Supabase cloud projects don't grant table privileges to `anon` or `authenticated`
  automatically, but the local stack does. Every migration therefore states its grants explicitly
  (`grant select, insert, … to authenticated`, `revoke all … from anon`), so local and cloud behave the same.

**Triggers:**
- `updated_at` / `updated_by` are stamped by a trigger, so client-supplied values are ignored.
- `on auth.users insert` creates a `profiles` row with `status = 'invited'`, plus an email sync on update.
- `plans_guard` rejects changes to `owner_id` and rejects `status → 'archived'` unless the caller is the owner.

### 4.3 RLS policies (summary)

All policies below are for the `authenticated` role. `anon` gets nothing.

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| profiles | `is_active_member()` | — (trigger) | own row only; **column grant limits it to `display_name`** | — |
| app_settings | `is_active_member()` | — (seeded) | `is_admin()` | — |
| music_pieces | `is_active_member()` (archived too; UI filters) | `is_active_member()` | `is_active_member()` | — (archive only) |
| arrangements | `is_active_member()` | `is_active_member()` | `is_active_member()` | — |
| plans | `can_view_plan(id)` | `is_active_member() and owner_id = auth.uid()` | `can_edit_plan(id)` + `plans_guard` | — (archive only) |
| plan_items | `can_view_plan(plan_id)` | `can_edit_plan(plan_id)` | `can_edit_plan(plan_id)` | `can_edit_plan(plan_id)` |
| plan_shares | `is_plan_owner(plan_id) or user_id = auth.uid()` | `is_plan_owner(plan_id) and user_id <> auth.uid()` | `is_plan_owner(plan_id)` | `is_plan_owner(plan_id)` |
| plan_links | `is_plan_owner(plan_id)` | `is_plan_owner(plan_id)` | `is_plan_owner(plan_id)` (revoke) | — |
| events | `is_active_member()` | `is_active_member()` | `created_by = auth.uid() or is_admin()` | same as update |
| event_plans | `is_active_member() and can_view_plan(plan_id)` | `can_edit_plan(plan_id)` | — | `can_edit_plan(plan_id)` |
| plan_activities | `can_view_plan(plan_id)` | `can_edit_plan(plan_id) and user_id = auth.uid()` | — | — |

**Storage (`storage.objects`, bucket `music-sheets`, private, 20 MB limit, `application/pdf` only):**
- SELECT: `bucket_id = 'music-sheets' and is_active_member()`. Every active member can already see the
  whole library, so sheet access equals library access.
- INSERT: `bucket_id = 'music-sheets' and is_active_member()`. Used through signed upload URLs (§4.5).
- UPDATE / DELETE: no user policy. Old-file cleanup runs server-side with the secret key.

Every helper returns false for a non-active member. A deactivated user's still-valid JWT therefore reads
nothing from the next request on.

### 4.4 Ordered, versioned plan edits

`reorder_plan_items(plan_id, expected_version, item_ids uuid[])` runs as one transaction:
1. `update plans set version = version + 1 … where id = $1 and version = $2`. If no row is updated, it raises
   `version_conflict`. If the user can't edit, RLS hides the row and the result is the same failure.
2. It verifies that `item_ids` is exactly the plan's item set, with no extras, no missing items and no
   duplicates.
3. One `UPDATE … FROM unnest($3) WITH ORDINALITY` rewrites all positions. The deferred unique constraint
   prevents transient collisions.
4. It inserts a `plan_activities` row and returns the new version.

`add_plan_item`, `remove_plan_item`, `update_plan_details` and `duplicate_plan` follow the same pattern.
`add_plan_item` also checks that the arrangement and its piece are `active` (spec §8.2).
`duplicate_plan` copies items but not shares, links or events.

### 4.5 Upload flow (changed from a server-proxied upload — see concern C1)

1. **`prepareUpload` (server action):**
   - Checks that the caller is an active member.
   - Validates the declared size against the limit and the name/extension.
   - Creates a music piece if needed and an `arrangements` row with `status = 'pending'`.
   - Returns a **signed upload URL** for `{music_piece_id}/{arrangement_id}/{upload_uuid}.pdf`.
2. **In the browser:**
   - Computes SHA-256 with Web Crypto. `prepareUpload` warns if the same hash or a similar title already
     exists (LIB-13).
   - Uploads directly to Supabase Storage.
3. **`finalizeUpload` (server action):**
   - Reads the first 1 KB and last 1 KB of the stored object through a range request.
   - Requires the `%PDF-` header and a `%%EOF` trailer, and a real size within the limit.
   - Marks the row `active`. On failure it deletes the object and the pending row.
4. **Leftovers:** pending rows older than 24 h are listed on an admin page with a "clean up" button. Users never
   see pending rows. There is no cron job.

Storage paths use a generated name, never the user's filename. Replacing a PDF (LIB-15):
- Upload a new object under the same `arrangement_id`.
- Swap `storage_path`, `original_filename`, size and hash in one update.
- Delete the old object.

The arrangement ID never changes, so plan references keep working.

### 4.6 Sheet viewing and public links

- **Members:** `GET /api/sheets/:arrangementId`:
  - Checks the session and active membership.
  - Creates a 10-minute signed URL and redirects (302) to it.
  - PDF bytes go straight from Supabase to the browser and never through a Netlify function (concern C2).
- **Public links:**
  - Token: 32 bytes from `crypto.randomBytes`, encoded base64url. Only `sha256(token)` is stored, and the raw
    token is shown to the owner once.
  - `/share/[token]` hashes the token and uses the **secret-key client** to load the link.
  - The link must not be revoked, must be unexpired, the plan must not be archived, and **the owner must be
    active**.
  - The page renders only the plan title and description plus, for each item: title, arrangement, key, notes.
  - `/share/[token]/sheets/:arrangementId` re-validates the token, checks that the arrangement is referenced by
    *that* plan, then issues a 302 to a signed URL.
- **Where the secret-key client is allowed:** exactly three places — public link resolution, admin member
  actions (`inviteUserByEmail`, ban/unban) and storage cleanup.

  - A small hand-written service worker (no framework plugin) caches the app shell and the plan view
    pages a member opens.
  - Opening a plan also stores its PDF sheets in Cache Storage, fetched once through the signed-URL
    route, so they open later with no connection. A plan page shows "Available offline" once its sheets
    are saved.
  - Offline, the app shows a banner and disables editing, uploading and sharing controls.
  - Sign-out clears the offline caches. A deactivated member's device keeps its copies until it next
    comes online and is signed out. That's an accepted limit of offline viewing.
  - iPhone/iPad: Safari can clear stored data for websites that haven't been used for about a week.
    Installed (Add to Home Screen) apps aren't affected, so members who need offline sheets should
    install the app.
  - Cost: sheets are downloaded once per device per version, which adds Supabase egress roughly
    proportional to plans opened. Still well within the free tier at this ministry's size.

**Milestone 3 notes (as built):**
- Plan reads and writes go through RLS; every edit goes through a `SECURITY INVOKER` function that
  locks the plan row, checks access and (for reorder, title/description and notes) the expected
  version. Errors use PostgREST `PTxxx` codes (404/403/409/422/423).
- The plan read policy checks `owner_id` on the row as well as `can_view_plan()`, because the helper
  can't see a row inside its own `INSERT … RETURNING`.
- The editor runs edits one at a time in a queue, updates the screen immediately, and rolls back on
  failure. A version conflict stops editing and asks for a reload, without overwriting.
- Drag and drop works with mouse, touch (drag handle) and keyboard, with spoken announcements that
  use song names.
- Offline (spec P9): `public/sw.js` keeps app code and the offline page; the plan page saves its own
  HTML, its sheets, the PDF viewer code and every script it loaded. Two pitfalls found in testing:
  files the browser serves from its memory cache never reach the service worker, and two separate
  `import()` calls of the same module can be split into different chunks. Both are handled.
- Sign-out removes plan pages, sheets and the saved-plans list; app code and the offline page stay.

## 7. Technical concerns, cost risks and ambiguities

### Technical concerns

| # | Concern | Impact | Proposal |
|---|---|---|---|
| C1 | **20 MB uploads can't go through Next.js on Netlify.** Server actions default to a 1 MB body; Netlify functions cap request payloads at about 6 MB. | LIB-01 breaks for large scans | Direct browser → Storage upload with a signed upload URL, then server-side validation of the stored bytes (§4.5) |
| C2 | Spec §9.3 suggests a server-side download route. Streaming PDFs through a Netlify function costs Netlify bandwidth and compute for every page view. | Burns Netlify free credits | The route only authorizes and **redirects**; the bytes come from Supabase |
| C3 | Deactivation versus existing sessions: a Supabase JWT stays valid until it expires (default 1 h), and signed URLs until their TTL. | Spec §3.3 asks for immediate loss of access "where feasible" | RLS checks `status` on every query (immediate for data). Ban the auth user (no refresh). Keep signed URL TTL at 10 min. Public links stop when the owner is inactive. Remaining exposure: a PDF URL already open, for up to 10 min |
| C4 | **Supabase's built-in email only sends to project team addresses and is heavily rate-limited.** Invitations and password resets won't reach members without custom SMTP. | M1 blocker | A free SMTP provider (e.g. Resend) plus a domain is required at M1, not M6 |
| C5 | Supabase Free **pauses after 7 days of inactivity** and has **no backups**. A two-week church break would take the app offline. | Reliability at launch | Free tier for development and pilot. Budget **Supabase Pro (~US$25/mo)** when the ministry starts relying on it, as the spec already says |
| C6 | Netlify's credit-based Free plan charges per **production deploy** as well as bandwidth and compute (verify current rates on the pricing page). Frequent pushes to `main` can use up the month. | Hard limit pauses the site | Develop locally and with deploy previews; merge to `main` per milestone, not per commit. Set a usage alert |
| C7 | RLS testing needs the local Supabase stack, which needs Docker. Docker is installed but not running. | Can't run `test:db` | Start Docker Desktop before M1 (dev machine only; nothing extra is hosted) |
| C8 | iOS Safari renders PDFs in an `<iframe>` inconsistently. | Mobile viewing | Use `react-pdf` everywhere (spec choice), load it lazily, and keep a "Download" fallback |
| C9 | Next.js 16 renamed `middleware.ts` to `proxy.ts`. | Spec §7.5 lists `middleware.ts` | Use `proxy.ts`; the helper keeps the spec's location under `lib/supabase/` |

### Cost estimates (free-tier fit)

- **Storage (1 GB):** sheet PDFs average roughly 0.3–3 MB, so about 400–1,500 arrangements fit. Scanned PDFs near
  20 MB fill it much faster.
  - This is the first limit you'll hit.
  - Consider lowering the default cap to 10 MB, or showing the file size at upload.
  - Replacement uploads delete the old file, so storage doesn't double.
- **Egress (5 GB/mo):** 15 musicians × 8 sheets × 1.5 MB × 5 services ≈ 0.9 GB/month. Comfortable.
  Signed URLs change on every open, so the browser cache doesn't help — acceptable at this scale.
- **Database (500 MB):** metadata only; years of headroom.
- **Recurring production estimate:** Supabase Pro $25/mo, plus domain about $1/mo, plus SMTP $0 (free tier
  covers invites and resets), plus Netlify $0 if within credits.

### Ambiguities in the spec (my proposed default in **bold**)

1. **Plan `published` status** has no defined behavior. → **Keep the value, add no behavior in the MVP** (it's
   only a label). Alternatively, drop it.
2. **Who manages events?** "creators and authorized members" is undefined. → **Creator or admin edits and
   deletes; any active member can create.**
3. **Events have no archive field**, but `archiveEvent` is listed. → **Hard-delete events; associations
   cascade; plans are untouched.**
4. **Archived music and RLS:** §10.1 says members read *active* music, but archived arrangements must still
   appear inside existing plans. → **RLS allows reading archived records; the UI hides them by default; they
   can't be added to plans.**
5. **Public links of a deactivated owner.** → **They stop working** (fits §3.3).
6. **Plans of a deactivated owner** — nobody can manage sharing. → **Shares keep working; add an admin "transfer
   ownership" recovery action in M6** (spec §3.2 recovery override).
7. **Who can duplicate a plan?** → **Anyone who can view it**; the copy is owned by whoever duplicated it.
8. **Who can attach a plan to an event?** → **The plan's owner or editors.**
9. **Event page shows plans the viewer can't access?** → **No; RLS hides them** (the page may show fewer plans
   for some members).
10. **Member email visibility:** share search needs it, so every active member can see every member's email.
    → **Acceptable for one church**; otherwise search by display name only.
11. **Tags and app settings storage** aren't in §8 → `tags text[]` and the `app_settings` table (§4.2).
12. **Invitation auth method:** password login (AUTH-03 implies it). → **Invite email → set password;** no
    magic-link login.
13. **Constitution vs. spec:** the constitution requires an installable PWA with a service worker; the spec only
    says responsive web app. → **Ship a web app manifest only (installable on iOS, Android and desktop Chrome);
    no service worker or offline caching.** Amend constitution Principle II to match (see §8).
